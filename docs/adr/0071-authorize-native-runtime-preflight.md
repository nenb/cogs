- Status: Accepted

- Accepted by: Delegated project lead on 2026-07-27 under Nick Byrne's standing authorization to complete all non-AWS work.
- Amendment scope: Bind implementation to exact feature predecessor `18f26441b6115091233d0c4cd44ced8f058d014f`; authorize exactly one `native-runtime-preflight` job in the existing `.github/workflows/ci.yml` and only the exact existing test-companion changes needed to run ADR 0070's portable/generated runtime tests on native Linux amd64 as namespace-local UID/GID 0 inside a trusted fixed mount/chroot sandbox; require the outer launcher to irreversibly restore the ordinary runner UID/GID, clear supplementary groups, set `no_new_privs`, and create fresh user, network, PID, and mount namespaces before the trusted namespace-root shell constructs that sandbox; remove every namespace capability before checked-out code; and set non-transferable excluded-surface highs. ## Context

The final runtime-discovery prototype closes the retained P1 corrections and P3 readability requirement within ADR 0070's unchanged per-file and 3,310 aggregate Phase B highs. Its portable and generated tests exercise the production primitives, but the current Darwin workstation cannot execute the Linux process path.

A local Linux/amd64 Docker process under QEMU reached the authentic production archive child. The child then invoked the required `close_range` syscall and received `ENOSYS`. This is an execution-envelope limitation, not authority to weaken descriptor closure. ADR 0070 permits no `close_range` fallback, and this decision adds none: descriptor enumeration, `/proc/self/fd`, `RLIMIT_NOFILE`, `os.closerange`, iterative close loops, a container-specific route, or acceptance of `ENOSYS` would invalidate the qualification.

The remaining pre-actual-size evidence therefore requires a native Linux amd64 kernel. Using the Phase B candidate workflow would improperly consume the one-shot `phase-b-runtime-discovery` event for a test prerequisite. The repository's ordinary CI workflow already has the right same-repository pull-request and quality-first boundary and can provide a fresh GitHub-hosted Ubuntu 24.04 execution without acquiring the pinned archives, entering any Kata lifecycle, or using KVM.

The checkout, exact-head verification, two direct trusted-sandbox invocations with fixed-shell output checks, and final clean-workspace verification are the complete job behavior. The literal namespace-root sandbox shell is trusted workflow launcher code, not a repository script or caller-selected command. Before either invocation enters `chroot`, it may perform only the fixed descriptor, mount, mount-verification, and `exec` operations below. The tests may create only the bounded local generated gzip/archive and fault fixtures defined below. They must remove those fixtures and every test owner, process, descriptor, state directory, report, export, and temporary object before success. Cleanup uncertainty fails the job; a final broad cleanup that hides a failed ownership proof is prohibited.

The fixed workflow shell must capture the runner UID and primary GID before privilege and interpolate only those validated decimal values into the fixed commands. Each invocation may use `/usr/bin/sudo -n --close-from=3` only to enter the exact absolute `/usr/bin/setpriv` launcher; no shell or checked-out code executes as host root. `sudo --close-from=3` must close every inherited descriptor numbered 3 or greater. `setpriv` must, before `unshare` and any namespace-root shell, set all real/effective/saved host UIDs to the captured runner UID, set all real/effective/saved host GIDs to its captured primary GID, clear every supplementary group, and irreversibly set `no_new_privs`. Thus the process entering `unshare` is the ordinary runner identity with no host-root capability, no supplementary `docker` or other control group, no inherited descriptor or supplementary-group authorization to a host Unix control socket, and no ability to regain privilege through a set-user-ID, set-group-ID, or file-capability executable.

That dropped process must create fresh user, network, PID, and mount namespaces using exactly `/usr/bin/unshare --user --map-root-user --net --pid --fork --mount` before the trusted shell runs. `--map-root-user` maps only the already-dropped runner UID and primary GID to UID/GID 0 in the new user namespace. The trusted shell initially receives capabilities only in that new user namespace so it can construct the mount/chroot boundary; it has no capability in the initial host user namespace and cannot join the host user, network, mount, or PID namespace. `--pid --fork` places the trusted shell and complete test tree in the new PID namespace.

The literal `trusted-sandbox-v1` shell must use `set -Eeuo pipefail`, fixed absolute host executable paths, quoted validated positional arguments, and no caller environment. It must close every descriptor numbered 3 or greater by enumerating and closing the numeric entries in its own `/proc/$$/fd` immediately on entry, make mount propagation recursively private, and then perform exactly this mount construction:

1. overmount host `/tmp` with a fresh namespace-private tmpfs and create a private staging mount there; this hides every host `/tmp` pathname socket before any checked-out code;
2. mount a fresh 16 MiB `mode=0700,nosuid,nodev` tmpfs as the future namespace root, create its `/sandbox`, and make `/sandbox` a bind mount backed only by that tmpfs;
3. create empty trusted targets and bind read-only only host `/usr`, host `/lib` and `/lib64` when each exists, and the already-verified exact checkout at `/src`; `/usr`, `/lib`, and `/lib64` must be `ro,nosuid,nodev`, and `/src` must be `ro,nosuid,nodev,noexec`;
4. mount a separate fresh 16 MiB `mode=1777,nosuid,nodev,noexec` tmpfs at `/sandbox/tmp` and a fresh read-only `nosuid,nodev,noexec` procfs for the new PID namespace at `/sandbox/proc`;
5. create an otherwise empty `/sandbox/dev`, bind only host `/dev/null` and `/dev/urandom` to their exact names, and remount both bindings read-only, `nosuid`, and `noexec`; and

The trusted shell must not copy a host file into the sandbox or create a device. Its only host-backed filesystem objects are the exact read-only binds above. After all mounts and exact-view verification, while the trusted old root is still available, it must repeat its explicit descriptor-3-and-above closure and immediately perform this exact terminal exec, with the companion path literal in each invocation:
