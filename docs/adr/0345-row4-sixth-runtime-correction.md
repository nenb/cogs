# ADR 0345: Row 4 sixth runtime correction

## Status

Accepted for source work after the failed attempt-one pair at exact protected-main candidate `533341db2cb4601fa47cf9ad0fbc92eb3b9036dd`. Those same bytes are retired as a Product/KVM dispatch candidate.

## Observations

Protected Product run `34782632633` attempt 1 failed in both profiles after each reached a stopped worker with a nonzero result at the old `runner.ts` line 655; the owner later emitted only the closed `helper` diagnostic. KVM run `34782634239` attempt 1 passed initial qualification and then failed driver readiness with `stderr-nul-cr`. Both runs are failed, non-authoritative, and non-authorizing.

A fresh local x86_64 Lima execution used diagnostic-modified bytes and is therefore diagnostic only, too slow for pass authority, and not a substitute for protected Product or KVM evidence. It established two bounded, deterministic design defects: two-second worker/skill reply waits can be starved behind the owner's measured 15-second synchronous helper-command bound, and, with diagnostic heartbeat headroom, Product reaches startup while the manager's four-second outer observation deadline can expire before Envoy's configured five-second startup window. Source review of the KVM failure identified an avoidable race in which `systemctl restart ssh` can disrupt an already-authenticated readiness session; the retained bytes do not prove that this race produced the observed carriage return. These observations prove only the Product timeout inversions and the KVM lifecycle risk; they do not prove a corrected pass, host capacity, isolation, readiness, or retirement.

## Decision

Make only the following corrections:

- account for each helper's complete 20-second service bound (15 seconds command observation plus five seconds for the two explicit two-second retirement waits and local overhead); use a 65-second initial gate-acquisition bound beyond its three-helper high and a separate 25-second snapshot-control acquisition bound beyond its one-helper high, while retaining the two-second runtime skill-lease ping/release deadline, validate and freeze the complete receipt and publication source identities once, and thereafter require their exact canonical/inode identities plus the retained exact worker/sandbox pidfds alive before every control admission instead of repeating helper-backed Docker inspection on the worker event loop; defer the periodic synchronous gate heartbeat until production startup and the asynchronous snapshot-control acquisition settle, then keep its cached-live reply bound at five seconds; use a 65-second owner peer-idle bound, a 105-second initial receipt-publication wait beyond the residual start helper plus four authentications, and 500-millisecond parent status sampling through the retained pidfd, followed after exact process exit by at most three exact-ID Docker state observations to allow daemon exit settlement; preserve byte, peer-identity, nonce, sequence, receipt, protocol, and full initial container checks;
- when the exact authenticated worker is stopped nonzero, terminate host custody with `diagnostic:"status"` and exactly one closed non-secret class: `application-exit` for application exit 1, `skill-gate-exit` for skill-gate exits 70–74, or `other-exit` for every other/signal-like exit; never project a raw exit value, output, log, exception, argv, path, or secret, and preserve cleanup uncertainty and false authority through TypeScript and workflow receipts;
- preserve the existing 1,000-millisecond runtime operation/revocation bound, add a separate explicit 20,000-millisecond manager startup-observation bound, and retain a 15,000-millisecond Envoy startup bound strictly inside it; keep the manager's existing operation-derived default for callers that do not supply the new startup bound and do not alter global maxima;
- stop and runtime-mask `ssh.socket` and `ssh.service` in one fail-fast early cloud-init transaction before fixed SSH configuration publication, creating the exact root-owned hold marker only after both operations succeed; require that marker, create and verify root-owned mode-0755 `/run/sshd`, validate the fixed daemon configuration, unmask, and start `ssh.service` exactly once during final setup; retain the active check and existing marker/fsync order, with no late reload/restart; preserve the single readiness command and strict UTF-8, NUL, and CR rejection without retry, normalization, stderr suppression, or stderr exposure.

No image definition, release pin, cap, allocation, source-inventory bound, or final-HGQ reserve changes.

Authorize only source implementation, focused review, full and readiness validation, protected PR CI, merge, and fresh disposable non-authorizing Product/KVM diagnostics with unique generations and exact cleanup. No dispatch or effect occurs now. A protected pair remains denied until the exact merged source and consumed image pass suitable Product and KVM diagnostics; host contamination or cleanup uncertainty stops that diagnostic lane. Only after that convergence, authorize exactly one fresh first-created attempt-one pair for the resulting protected-main bytes: one Protected Product run and one KVM qualification run. Same-byte retry remains denied. H, G, Q, AWS, OpenTofu, SSM, deployment, and every other Docker/KVM/network effect remain denied.
